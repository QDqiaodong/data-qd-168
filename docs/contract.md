# Locale bundle contract v1

A localization maintainer provides default_locale, catalogs, fallback and requested. Locale names are opaque nonblank identifiers (not a BCP-47 normalizer). Each locale maps message keys to {value,variables}; variables declares exactly the named placeholders appearing in value, with types string or integer. Repeated placeholders are legal; escaped braces are literals. Only Python-format simple identifier fields such as {name} are permitted; positional fields, attribute/index access, conversions, format specs and unmatched braces fail. Literal empty strings are valid translated messages and do not trigger fallback.

Default catalog must be nonempty. All keys and variable type maps in translations must agree with the default. Fallback is a single-parent directed graph between declared locales; default has no parent. Missing explicit parent means the default. Cycles are rejected even if their locales are not requested. Every requested locale must exist and be unique. Compilation resolves every default key along the chain, saving source_locale and a diagnostic for each fallback. This is deterministic offline resource construction, not machine translation, plural-rule evaluation or ICU MessageFormat support.

render(message, variables) validates the exact variable set and types before formatting. bool does not satisfy integer. Compilation validates the whole input before atomic publication. The sample resolves fr-CA greeting from fr, cart from fr-CA; rendering greeting with name=Ada yields Bonjour Ada.

# Reviewed history contract v2

compile_reviewed_history(data) and the locale-bundle-history CLI build per-query historical catalog views from an append-only fact log, so a maintainer can ask "which translations were approved as of business time `at`, given only the facts known up to sequence `known_seq`". The v1 message, fallback-chain, placeholder-safety and CLI protection rules are unchanged and reused.

Input fields are exactly default_locale, locales, fallback, requested, sources, translations, reviews, queries. locales holds up to 100 distinct identifiers and contains default_locale. fallback keeps the v1 single-parent rules: an omitted parent means the default locale, the default has no parent, and cycles are rejected even for unrequested locales. requested is a nonempty list of distinct declared locales.

Fact rows are exact-field objects. sources: {id,seq,effective,key,value,variables}. translations: {id,seq,effective,locale,key,source_id,value,variables} with a declared non-default locale. reviews: {seq,effective,translation_id,approved} with approved strictly boolean. queries: {id,at,known_seq}, 1 to 100 rows with distinct ids. Times and seqs are non-boolean integers; times start at 0, seqs at 1, both capped at 10^9. Source/translation ids are globally distinct, fact seqs are globally distinct across all three kinds, and input list order carries no meaning. A translation must reference a source revision with a smaller seq and repeat that revision's key and variable type map; a review must reference a translation with a smaller seq. Every message value passes the v1 placeholder safety rules, including facts no query uses. Totals: at most 10000 facts, 10000 distinct source keys. Empty default and translation values are valid.

A query sees only facts with effective <= at and seq <= known_seq; late facts carrying an earlier effective are legal, and facts outside the cutoff must not leak in, even through existing references. The current source revision of a key and the current translation revision of a (locale,key) are the visible rows with the greatest (effective,seq); a query with no visible source revision at all is invalid. A translation's review state is its visible review with the greatest (effective,seq): absent means pending, approved=false means rejected.

translation_states covers every non-default locale x every current source key, sorted by locale then key, as rows {locale,key,translation_id,review_seq,state} with nulls where no fact exists. state is missing with no visible translation, else stale_source when the selected translation's source_id differs from the current source id (this wins over review state), else the review state pending/rejected/approved. An approval authorizes only the exact translation id against the exact source revision id: a new source revision never inherits an old approval, even with identical text, and a pending/rejected/stale newer translation never resurrects an older approved one for the same locale and key.

Catalog compilation treats only translations approved within the same query as existing, then walks the v1 single-parent chain per key to the nearest available locale; the default locale serves the current source revision and needs no review. An approved empty-string translation is present and blocks fallback. Old translations only have to match the variable types of the source revision they reference, so a source type change makes them stale and resolution falls through instead of rejecting the input. Each resolved message carries value, variables, source_locale plus source_id (current source revision), translation_id and review_seq (the approving review); the last two are null for default-locale resolutions.

Output is {views:[...]} in query input order; each view is {query_id,at,known_seq,default_locale,catalogs,fallback_messages,translation_states}. catalogs contains only requested locales; fallback_messages lists requested-locale keys that fell back, sorted by locale then key. The whole input is validated before any view is emitted; any invalid fact or query fails the run with exit 2 and preserves the previous report. The 8MB read cap, duplicate JSON key and non-finite number rejection, source/output distinction, symlink refusal and atomic replacement all match v1.

# Release bundle contract v3

compile_release_bundles(data) and the locale-bundle-release CLI answer "which messages does each application actually ship?" when several applications share components. A maintainer supplies the v1 fields default_locale, fallback, catalogs and requested plus components and applications; the v1 message, placeholder-safety, fallback-chain, locale-identifier and validation rules are reused unchanged (input validation is shared with compile_bundle, so the two commands accept exactly the same catalog/fallback inputs).

Input fields are exactly default_locale, fallback, catalogs, requested, components, applications. components is a list of at most 10000 exact-field objects {id,requires,keys}: id is a unique opaque identifier, requires is a list of component ids, and keys is a list of message keys that must exist in the default catalog. applications is a nonempty list of at most 10000 exact-field objects {id,roots}: id is unique and roots is a list of component ids. Duplicate component ids, application ids, dependency entries within one requires, key entries within one keys, and root entries within one roots are rejected. Every requires target, root and component key must resolve; components may be unreferenced. The dependency graph is directed component -> requires and must be acyclic across the whole declared graph, even over components no application reaches.

For an application, the included key set is the union of keys declared by every component in the transitive closure of its roots. A component reached by several paths, or shared by several applications, still contributes its keys once per application; keys declared by one application's closure never appear in another application's package. All included keys are validated against the default catalog during input validation.

Per application and requested locale, each included key is resolved independently along the v1 fallback chain; the source locale that actually supplied the message is recorded as source_locale, and empty-string translations are present and block fallback exactly as in v1. Fallback diagnostics report only keys included in that application's package and only for requested locales. A key whose fallback source equals the requested locale produces no diagnostic. There is no cross-application or cross-locale diagnostic deduplication beyond what each (application, locale, key) naturally implies.

Output is {applications:[...]} sorted by application_id. Each application is {application_id,catalogs,fallback_messages}. catalogs contains only requested locales; within each locale messages are sorted by key, and each message carries the v1 value, variables and source_locale plus included_by: the deduplicated, sorted ids of components in that application's closure that directly declare the key. fallback_messages is sorted by locale then key, and each row is {locale,key,source_locale,included_by} with the same included_by semantics. Every included key appears in every requested locale's catalog for that application.

The whole input and every application/locale package is built before publication; any validation, dependency, or package-build failure exits 2 and leaves the previous output untouched. The 8MB read cap, duplicate JSON key and non-finite number rejection, source/output distinction, symlink refusal and atomic replacement all match v1.

# Work queue contract v4

locale-bundle-work-queue keeps a single-operator offline dispatch ledger in one local JSON file, so a localization lead can sync reviewable work out of the fact log, dispatch it to translators, and confirm completions without hand-comparing tasks. Four subcommands exist: sync, assign, confirm, query. The v1 message/placeholder rules, the v2 fact-log rules and the v3 component-graph rules are reused unchanged; work-queue operations never modify review facts or release bundles.

sync --source INPUT --ledger LEDGER --query QID reads an input whose fields are exactly the v2 history fields plus components and applications. Components and applications follow the v3 structure and limits with two changes: a component key must exist among the source-fact keys (there is no default catalog here), and applications may be empty because it is the complete application scope of this sync. Only the selected query's at and known_seq compute current source revisions and review states; the remaining queries are inert data, and only the selected query must see at least one source revision. Both cutoff values must be greater than or equal to the ledger's last accepted values; any rollback rejects the sync and leaves the ledger untouched, while equal cutoffs may re-sync the application and language scope. The first successful sync may create the ledger.

An application's used keys are the transitive closure of its root components; a key declared in the graph whose source revisions are not yet in effect at the cutoff is not dispatched. The language scope is the non-default locales of requested, and every (locale, key) slot is judged by that locale's own review evidence even when the v1 fallback chain could serve another locale's translation.

One task per (locale, key, source_id): a key reached through several paths or shared by several applications still yields a single task recording the affected application set. New tasks are created only for in-scope revisions not approved at the cutoff. When the dependency or language scope changes, affected sets are updated while the same revision keeps its assignment and audit; a task that leaves the scope entirely rejects manual operations but keeps its records, and the same revision re-entering reuses the original task, re-judging by current review evidence whether its completion still holds. When the current source revision of a key moves on, the old task is archived (even if already out of scope) keeping its assignee and confirmation audit, and if the new revision is not approved a fresh unassigned task is created.

Review evidence drives the work status: an open task whose translation becomes approved moves to pending_confirm, and only a manual confirm completes it. A later sync that finds the approval revoked reopens the task to open, keeping the translator and the old confirmation audit; if the translation or its approval is replaced by different evidence, the old confirmation cannot keep the task complete either, even when no rejection was visible between the two syncs.

assign --ledger L --locale X --key K --source-id S --translator T targets the exact revision; only in-scope, currently incomplete tasks can be assigned. Assignment records the translator and completes nothing. confirm --ledger L --locale X --key K --source-id S --confirmer C --translation-id T --review-seq R requires both evidence fields to equal the task's current approval; the confirmation audit keeps the confirmer and the evidence used. Repeating a confirmation with the still-current evidence appends no event. Manual operations on archived revisions, out-of-scope tasks, or stale approval evidence are rejected and the ledger is preserved.

A sync in which the query, cutoff, scope and task-relevant facts are all unchanged (including reordered equivalent input) appends no audit, creates no task and overwrites no manual action; only successful syncs with changes record the query and cutoff they used. query --ledger L prints the ledger: task identity, current review state and approval evidence, work status, assigned translator, affected applications, the last accepted query and cutoff, and the archive and manual-operation history.

The ledger file follows the same local JSON safety rules: the 8MB read cap, duplicate JSON key and non-finite number rejection, full validation before atomic replacement, and symlink refusal; bad input, a corrupt ledger or a rejected operation exits 2 and leaves the old file untouched.
